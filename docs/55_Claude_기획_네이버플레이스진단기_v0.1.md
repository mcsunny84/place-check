# 55. 네이버 플레이스 진단기 기획 v0.1

- 작성: 2026-09-14, 서버 세션(Claude). 검토자: Codex(gpt-6-astra).
- 발제: 태양 — "네이버 플레이스 주소를 넣으면 얼마나 잘 만들었는지 확인·분석하고, 추가로 할 일을 제안하는 도구. SEO·GEO·AEO 진단처럼. 나와 비슷한 사업자들에게도 배포하고 싶다."
- 검토 범위(태양 원칙, 53·54번과 동일): 적대 검증은 **데이터 취득 경로의 계약 정합성·채점 결정론·구현 정확성**에만. 표현·사업성은 검토 대상 아님. 단, 이 문서는 기획 단계이므로 §7의 결정 항목에 대한 **근거 있는 반론**은 환영한다.

## 0. 정독 결과 — 이미 있는 것과 새로 필요한 것

이 제품은 백지가 아니다. 상용화 기획(commercial-plan 04·06번)의 SEO 축 S1(플랫폼 프로필 위생)·S3(NAP)·S5(평판 운영)가 곧 "플레이스 진단"이고, 53번(2026-08-30)이 네이버 파생 요약의 저장·표시를 내부 범위에서 개방했다. 따라서 새 축을 만들지 않고 **S1·S5를 플레이스 전용 체크리스트로 구체화**하는 것이 본 기획의 본체다.

## 1. 제품 정의

**"내 네이버 플레이스가 얼마나 채워져 있고, 무엇부터 채워야 하는지"를 한 화면에 보여주고, 채울 초안까지 만들어 주는 도구.** 순위 예측·보장 없음. 우열 비교 없음. 점검 대상은 사장님이 스마트플레이스에서 **직접 통제할 수 있는 항목**만.

입력: 상호 + 지점(또는 지역). 플레이스 URL은 선택 입력 — placeId는 참고 기록용이며 자동 판독에 쓰지 않는다(§3 경로 C 제외 사유).
출력: ① 완성도 점수(coverage 충족 시) + 그룹별 신호등 ② "지금 가장 아픈 것 1개, 이번 주 할 일 3개" ③ 항목별 처방 카드(왜·무엇을·초안 생성 버튼) ④ 14일 뒤 재진단 예약.

## 3. 데이터 취득 경로 — 이 기획의 핵심 쟁점

| 경로 | 내용 | 계보 | 지금 가능한가 |
|---|---|---|---|
| **A. 지역검색 API 파생 요약** | naver_presence + blog/local 규모 수치 | 플랫폼(naver) — **53번으로 내부 저장·표시 개방** | 내부·파일럿: 가능. 외부 배포: TERMS_APPROVED 전 불가(HANDOFF §4.6) |
| **B. 사장님 자가 증빙** | 본인 스마트플레이스 관리 화면을 보고 문항에 답함(또는 캡처 업로드 후 답 확인) | 06번 P-9 v2: 사실의 원천이 플랫폼 화면이므로 **platform_state** | 세션 내 표시·"할 일" 안내: 가능. **저장·채점·추이: 승인 전 불가(unknown)** — 이것이 06번 12라운드 합의 |
| C. 공개 플레이스 페이지 자동 판독 | m.place.naver.com 렌더 후 파싱 | 약관 불확실 + 순위추적기 실사례(8/19 이후 캡차 전면 차단, 8/26 5/6 실패) | **MVP 제외 유지**(06번 S1 결정). 재현 불가·차단 리스크 |
| D. 스마트플레이스 소유자 API | — | — | 공개 API 없음. 제외 |

**결론**: A는 내부용으로 바로 쓰고, B가 배포용의 유일한 경로다. 그런데 B는 06번 계약상 승인 전 채점 불가다. 그러면 "배포용 도구"는 승인 전엔 점수를 못 보여준다.

이 모순을 푸는 설계가 §4의 **Tier 0(무저장 셀프 진단)** 이다.

### Tier 0의 정당화 (검토 요청 Q2 — 가장 세게 공격받아야 할 부분)

- 06번 P-9 v2가 금지한 것은 "**우리 시스템이** 플랫폼 화면 상태를 저장·채점·추이에 쓰는 것"이다. Tier 0은 우리 시스템이 아무것도 받지 않는다. 사장님이 종이 체크리스트에 체크하고 스스로 합계를 내는 것과 구조가 같다.
- 06번이 승인 전에도 허용한 "세션 내 표시 + 할 일 안내(무저장)"의 최대치가 정확히 이것이다.
- 화면 문구 계약: 점수 옆에 "이 점수는 사장님이 직접 답한 내용의 집계입니다. 저희가 네이버에서 확인한 값이 아닙니다"를 고정 표기(fixed_ui). "네이버 점수", "노출 점수" 같은 명칭 금지.
- 리스크: ① 사장님이 잘못 답하면 점수도 틀림 — 자가 진단의 본질이고 고지로 해결 ② "체크리스트 문항을 플랫폼 화면 구조대로 만들면 간접 전사"라는 12번 P2-10 논리가 **무저장이어도** 적용되는가? 나는 "전사"의 해악은 저장·축적에 있다고 보아 적용되지 않는다고 판단한다. 반론 환영.

### Tier 0 → 1 승급 흐름

Tier 0 결과 화면 하단에 "자동 진단 신청(파일럿)" 링크. 눌러도 답변은 넘어가지 않는다 — 06번 "사후 승격 불가"와 일관되게 Tier 1에서 새로 받는다.

## 6. 배포 형태

- **Tier 0**: 정적 HTML 1개 (`public/place-self-check.html`). 의존성 0, 서버 0. 상태 페이지처럼 gist·githack 또는 marketing-lab 공개 경로로 배포. 채점 함수는 `lib/place-scoring.js`를 UMD로 빌드 없이 그대로 로드(geo-lanes-view.js 패턴). 로컬스토리지에도 저장하지 않는다(브라우저 닫으면 소멸) — "무저장"을 문자 그대로.
- **Tier 1**: marketing-lab 서버(4747)에 `/place.html` + `POST /api/place/analyze`. 기존 job-commit·publish-gate 경유.
- 배포 전 게이트(HANDOFF §4.6): Tier 0은 "리포트 파일 전달"도 "유료"도 아니고 네이버 데이터 0건이므로 게이트 대상이 아니라고 본다. **[검토 요청 Q3]**

## 8. 검토자에게 — 공격해 달라는 지점

- **Q1** D3(블로그 규모 절대 수치)가 "우열 점수화 금지"를 위반하는가.
- **Q2** Tier 0(무저장 셀프 진단)이 06번 P-9 v2·12번 P2-10의 "간접 전사" 논리를 실제로 피하는가. 피하지 못한다면 어떤 문항 구조로 바꾸면 피하는가.
- **Q3** Tier 0이 HANDOFF §4.6 외부 제공 게이트 대상인가.
- **Q4** 항목표에서 결정론 판정이 실제로 성립하지 않는 항목(사장님이 답할 수 없거나 모호한 것)이 있는가.
- **Q5** 처방 우선순위 규칙(배점×상태)이 실용상 엉뚱한 "이번 주 할 일"을 내는 반례가 있는가.
- 형식: Issue ID `R1-n`, 심각도 Blocker/Major/Minor, 각 이슈에 근거 문서·조항 인용. Blocker는 실제 계약 위반·결정론 불성립에만. 수렴 목표 3라운드.

## 9. 태양 결정 추가 (2026-09-14, 55번 작성 직후)

- **배포 대상·형태 확정**: 동종업계 사장님 약 2,000명 오픈채팅방에 **무료 배포**. "내가 만들었으니 써보세요" 방식.
- **검토 강도 완화 지시**: 무료 배포이므로 보안·약관 등 비기능 항목을 과도하게 타이트하게 보지 말 것. 적대 검증은 **동작 정확성(채점 결정론·처방 매핑·계산 오류)** 에 집중. 약관 보수 해석을 이유로 한 Blocker는 두지 않는다 — 53번과 같은 사업 판단(태양 소유).
- 따라서 §7 D1은 **승인(예)**. Tier 0을 첫 배포판으로 한다.
- 실무 제약 1개만 유지(법적 아님, 운영 현실): 2,000명이 동시에 쓰는 경로가 우리 서버·네이버 API를 거치면 일일 호출 한도와 캡차 차단이 실제로 걸린다. Tier 0(정적·무서버)이 이 문제를 구조적으로 피한다. Tier 1(API 자동 진단)은 오픈채팅 공개 전 호출 한도·큐 설계가 선행돼야 한다.
