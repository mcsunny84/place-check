# 09. GPT 코드 리뷰 v1

- 검토: Codex, 2026-09-15. 범위는 동작 정확성과 설계·모듈 계약 일치. 약관·보안 정책·사업성·표현 취향은 제외했다.
- 기준: 06번 §1~3, 08번 계약, 07번 추가·3차 실측. A1 비공개 번호, A3 요일 규칙, A4 `base.road`, B6/C3 첫 페이지 사용은 07번의 의도된 변경으로 취급했다.
- 현재 작업 트리의 07번은 **3차 실측에서 끝난다**. `server.js:124`가 인용하는 “07번 4차 실측”, GraphQL 정렬·커서 계약은 이 파일에 없다. 해당 API의 실제 응답 보장은 네트워크 금지 조건상 검증하지 않았다.
- `.env` 내용은 읽지 않았다. 서버 import의 자동 읽기도 하네스에서 차단했다. 실제 fetch는 금지하고 기존 픽스처·주입 함수·메모리 파일시스템·가짜 타이머로 확인했다. 저장소 구현·기존 테스트는 수정하지 않았다.

## 0 총평

**불가 — 현재 버전 그대로의 배포는 보류.** C-1에서 실제 캐시 결과 손실과 수집 세대 혼합을 재현했다. 90초 종료 범위, 리뷰 완전성, D3 판정 우선순위, KST 날짜에도 결과를 바꾸는 결함이 있다. C-1과 핵심 Major 수정 후 재검토가 필요하다.

기본 구조의 장점은 있다. 수집 pump는 직렬이며 `finally`로 running을 해제한다. 일반적인 성공·비차단 실패·차단 경로에서 jobs/queue 정리는 이루어진다. `BUDGET=11`은 명시적 수집 호출 기준으로 감소하고 리뷰 GraphQL은 최대 6회다. 홈·2탭·리뷰 6회·쿠폰 1회는 10회, 단축 해석 포함 11회이며 탭 재시도도 예산을 차감한다. 검색광고 호출은 이 수집 예산 밖이다. 다만 실제 HTTP redirect 횟수까지 세는 구조는 아니다.

A1 `phonePrivate=true`와 A4 `road` 판정은 3차 실측을 반영했다. B6의 hasMore 무관 판정, C3의 둘째 페이지 이후 EVENT 누락 가능성도 명시된 변경·한계 자체를 결함으로 세지 않았다. 직접 URL의 10분 refresh 경계와 캐시 hit의 쿨다운 우회는 구현되어 있다.

LLM 문자열·리뷰 본문 발췌는 `esc()`를 거쳐 삽입된다. `<img src=x onerror=alert(1)>`를 리뷰 요약에 넣은 렌더링에서는 태그가 이스케이프됐다. **검토한 사용자 본문→화면 경로에서 실행 가능한 XSS는 확인하지 못했다.** 통계 숫자 등은 타입 검증을 전제로 직접 삽입되므로 아래 결과 검증 보강 시 함께 정규화해야 한다. JSON 형식 보장은 내용의 진실성이나 프롬프트 주입 방어와 같지 않다.

테스트 실행 결과와 방법은 §2에 기록한다. Ubuntu 시스템을 실제로 변경하거나 외부 서비스에 접속하지 않았으므로 배포 검토는 정적 경로 분석이다.

## 1 이슈

### C-1 | Blocker | server.js:325, 352–355

- **문제:** 수집 합류는 LLM·검색량 결과 생성까지 보호하지 않는다. 같은 매장의 동시 응답이 각각 LLM을 호출하고, 나중 응답이 성공 캐시를 삭제하거나 새 facts에 옛 분석을 붙인다.
- **재현·근거:** 메모리 캐시에서 동일 facts로 `buildResponse()` 두 개를 시작하면 키워드 LLM 호출은 2회다. 첫 호출이 성공한 후 둘째가 null을 반환하면 `keywords_llm: undefined`가 기존 성공값을 덮고 JSON 직렬화에서 사라진다. 다른 재현에서는 옛 facts의 LLM을 대기시킨 뒤 이름이 `NEW`인 facts를 저장하고 옛 LLM을 완료하자 캐시는 `name=NEW`, `keyword=OLD`가 됐다. `readCache(pid) || facts`는 최신 facts 필드는 보존하지만, 분석의 수집 세대 일치나 기존 성공값은 보장하지 않는다. 합류한 모든 응답에 `facts.fresh`가 전달되어 통계도 요청 수만큼 중복 기록된다(334–336).
- **최소 수정:** `(placeId, 수집 generation)`별 분석 Promise를 공유한다. 완료 시 현재 캐시의 generation과 일치할 때만 저장하고, 실패한 필드는 기존 성공값을 삭제하지 않는다. 통계는 응답 생성이 아니라 수집 완료에서 한 번 기록한다. 실패 재시도에도 짧은 backoff를 둔다.

### C-2 | Major | server.js:161–175, 193–229, 396, 415–424

- **문제:** “접수 후 최대 90초”가 전체 요청 마감이 아니다. 타이머는 수집 payload가 오면 해제되고, 그 뒤 LLM 3종 및 순차 검색광고 배치는 무제한으로 기다린다. 캐시 hit는 처음부터 마감 타이머가 없다. 수집 중 대기자가 모두 timeout돼도 추가 탭·리뷰·쿠폰 요청을 계속 시작한다.
- **재현·근거:** 가짜 타이머로 홈 fetch 도중 90초 마감을 발생시키면 클라이언트는 timeout을 받지만 이후에도 fetch가 이어져 총 4회가 실행됐다. `collectReviews(job, ...)`는 job을 받으면서도 대기자·마감을 읽지 않는다. `Promise.all`의 한 LLM이 미완료면 전체 응답도 미완료다. 세 모듈의 SDK 호출에는 이 요청의 남은 시간에 연결된 signal/timeout이 없다. 미실행 작업은 대기자 0이면 제거되지만 진행 작업은 종료까지 슬롯을 차지한다. 연결 종료도 대기자 제거에 연결되지 않는다.
- **최소 수정:** 접수 시 deadline을 정하고 캐시·수집·분석·검색량을 모두 포함한다. 대기자별 종료와 job별 활성 대기자를 추적하고 fetch 시작 직전, gap 대기 후, 재시도·페이지마다 확인한다. 수집이 끝난 뒤 남은 시간이 부족하면 LLM/검색량은 규칙 기반 결과로 종료한다. 연결 종료도 정리한다.

### C-3 | Minor | server.js:95–101, 407–409

- **문제:** IP 제한이 “새 수집 3회/분”이 아니라 캐시 miss 요청 3회/분이다. 기존 작업 합류와 busy 거절도 한도를 소비한다. `ipLog`의 IP 키는 만료 후에도 삭제되지 않는다.
- **재현·근거:** 동일 IP의 같은 placeId 동시 요청 4개는 새 job 하나인데 네 번째가 429다. `ipAllowed()`가 `enqueue()`와 합류 판별보다 먼저 실행된다. 각 IP 배열만 재방문 때 정리하며 Map 자체는 계속 증가한다.
- **최소 수정:** 합류를 먼저 판단하고 새 작업을 실제 접수할 때만 카운트한다. 시간 기준으로 만료 IP 엔트리를 제거한다.

### C-4 | Major | server.js:166–185

- **문제:** 리뷰 페이지네이션 실패·예산 소진·커서 이상을 “180일 수집 완료”로 잘못 표시한다. 반복 cursor 방지도 없고, 정규화 결과가 비면 마지막 원소 접근에서 예외가 난다.
- **재현·근거:** 첫 페이지 50건 성공 후 둘째 페이지 timeout을 주입하면 `fetched:50, complete:true, from:180일 전`이 반환됐다. 완료 여부를 중단 원인이 아니라 `all.length < 300`으로 계산하기 때문이다. 같은 50건·같은 cursor를 계속 받으면 6회까지 중복 요청하고, dedupe 전 건수를 fetched로 쓴다. 50개 항목이 전부 id 누락이면 `norm[-1].cursor`에서 예외가 나고 외부 catch에서 조용히 SSR로 돌아간다. GraphQL 변수에 정렬 기준이 없고, 한 건의 오래된 방문일만으로 중단하는 근거도 현재 07번에는 없다.
- **최소 수정:** `exhausted / cutoffReached / pageLimit / budget / timeout / badCursor / malformed` 중단 사유를 기록한다. 검증된 정상 종결일 때만 complete로 표시하고, seen cursor와 정상화된 마지막 항목을 검사한다. fetched는 실제 고유 건수로 표시하며 incomplete일 때 실제 수집 범위를 사용한다. 방문일 기반 조기 종료는 그 날짜의 내림차순 보장이 있을 때만 쓴다.

### C-5 | Major | server.js:179–185; lib/facts-to-answers.js:157–170

- **문제:** 분석용 180일 리뷰 창을 점수 판정에도 재사용하여 D1의 오래된 리뷰가 사라진다. D2는 방문일순 일부 표본만 보고 전체 최신 답글 또는 “답글 없음”을 확정한다.
- **재현·근거:** 총수 1, 마지막 리뷰가 181일 전인 SSR·GraphQL 응답을 주면 GraphQL 결과가 한 건이라도 있는 경로에서는 180일 필터가 SSR까지 제거한다. `reviews=[]`가 되어 D1 unknown으로 처리되지만 계약은 fail이다. 또한 최근 표본 전부 무답글이어도 더 오래된 리뷰에 어제 답글을 달았을 수 있다. 표본의 최신 답글이 100일 전이라는 사실도 전체 최신 답글이 100일 전임을 증명하지 않는다. 기존 테스트는 “최근 20건 전부 무답글→fail”을 고정한다. 07번의 리뷰 자동 수집 승격 자체는 이 완전성 증명을 제공하지 않는다.
- **최소 수정:** D1용 최신 관측 날짜는 분석 창 필터 전에 별도로 보존한다. D2는 최신성 또는 답글 부재를 증명하는 원천을 사용한다. 그 전에는 관측한 최근 답글로 pass를 확정할 수 있는 경우 외의 부정 판정은 unknown/보충 질문으로 둔다.

### C-6 | Major | lib/facts-to-answers.js:174–180

- **문제:** D3가 06번 §1.1의 “검출 우선”을 위반한다. 반대로 소식 목록만 읽히면 각 소식 본문이 missing이어도 검사 완료로 간주한다.
- **재현·근거:** `description=value('리뷰 작성 시 무료 쿠폰'), feeds=missing`은 사전에 검출되는 문구인데 unknown이다. `description=value('정상'), feeds=value([{createdAt:'2026-09-15'}])`는 desc가 없는데 pass다. 본문 누락을 `(f.desc || '')`로 빈 문장으로 바꾼다.
- **최소 수정:** 읽힌 원문은 먼저 검사하고 검출되면 즉시 fail. 미검출 pass는 description과 검사 대상 소식 각각의 본문이 value/확인된 empty일 때만 허용한다.

### C-7 | Major | lib/facts-to-answers.js:135–147; lib/coupons.js:28–37

- **문제:** 기간 없는 EVENT를 최근 90일이라는 이유로 진행 중으로 확정한다. 이는 “기간 missing→unknown” 계약과 다르고 07번의 첫 페이지 판정 변경에도 없는 추정이다. 읽지 못한 쿠폰 배열을 빈 배열로 바꾸어 홈의 긍정 증거를 지우는 경로도 있다.
- **재현·근거:** 쿠폰 0, EVENT의 createdAt만 오늘이고 기간 없음이면 C3 pass다. 한쪽 기간만 있으면 active=false가 된 뒤 fail까지 확정된다. 또한 `normalizeCoupons({total:1})`는 `coupons:[]`를 만들고, facts-to-answers는 이 길이 0을 홈 `hasCouponCount=1`보다 우선한다. 쿠폰 절대 기간 없이 길이/count만 캐시하므로 cache hit의 새 asOf로 쿠폰 만료를 재판정할 수도 없다.
- **최소 수정:** EVENT 기간 불명은 unknown으로 유지한다. 쿠폰 배열 누락과 실제 빈 배열을 구분한다. 쿠폰 count의 긍정 증거를 유지하되, 06번의 날짜별 재판정을 제공하려면 절대 start/end를 저장한다. count만 사용하는 제한을 유지한다면 그 제한과 TTL을 계약에 명시한다.

### C-8 | Major | lib/place-parse.js:230–239; server.js:163; public/index.html:177

- **문제:** 서버 리뷰 날짜 추정과 브라우저 직접 체크 날짜가 KST 달력일 계약을 어긴다.
- **재현·근거:** TZ=UTC에서 `reviewDate('9.15.화','2026-09-15T00:30:00+09:00')`는 **2025-09-15**다. 로컬 달력일 9/14와 비교해 올해 오늘을 미래로 보아 작년으로 내린다. 브라우저 TZ=Asia/Seoul, 9/15 01:00에서 `today()`는 **2026-09-14**다. 로컬 offset을 더한 뒤 다시 UTC ISO로 자르기 때문이다. 수집 cutoff도 UTC 날짜를 쓴다. `reviewDate('2026.2.31.화', ...)`는 존재하지 않는 `2026-02-31`을 반환한다.
- **최소 수정:** 서버·브라우저 공통으로 epoch에 9시간을 더해 UTC getter/ISO로 KST 날짜를 얻는다. 월일은 실제 달력 유효성을 검사한 뒤 연도 추정을 수행한다. cutoff 역시 KST 달력일에서 계산한다.

### C-9 | Major | lib/place-parse.js:75–99, 248–271; lib/facts-to-answers.js:38–44

- **문제:** 일부 원천 누락이 부재·완료로 승격된다. 영업일수는 유효 요일 집합 대신 배열 길이로 A3를 판정한다.
- **재현·근거:** `homepages:{}`는 원천 URL 키들을 읽지 못했는데 empty가 되어 B7 fail이다. visitorReviews query 키가 있으나 `items`가 없거나 참조가 미해결이어도 `reviews=value([])`가 된다. `breakHours` 누락은 `[]`로 바뀌어 “휴게 없음”과 같아진다. 월~토에 월요일 행이 중복된 7행은 A2 일부, A3 n/a가 된다. 07번 규칙은 행 수가 아니라 요일 수다.
- **최소 수정:** 컨테이너 존재와 하위 필드 판독 완료를 분리한다. 리뷰 query의 items 미해결은 missing으로 유지한다. 유효한 월~일 집합과 휴게 정보의 관측 상태로 A3를 판정한다. 실제로 읽힌 null/빈 배열만 empty로 인정한다.

### C-10 | Major | server.js:309–318; lib/draft-analysis.js:43–47, 77

- **문제:** 자동 초안·LLM 입력에 원천과 다른 영업 사실을 넣는다.
- **재현·근거:** `parkingInfo='주차 불가'`가 LLM 프롬프트에서는 **주차: 가능**이다. 비어 있지 않은 문장 전체를 참값으로 취급한다. 편의시설 `['포장']`은 “배달은 하지 않습니다”로 바뀌며, 필드가 missing이어도 server가 빈 배열로 바꿔 포장·배달 false를 넘긴다. 월 10~18시, 화 12~20시는 “월~화 10~18시”로 출력된다. 전체 초안의 찾아오는 길에는 올바른 `road` 대신 07번에서 오매핑으로 확인한 `accessor`가 여전히 전달된다.
