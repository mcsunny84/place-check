# 플레이스 체크 (place-check) — 온라인 무료 배포판 기획 v0.5

- 작성: 2026-09-14 저녁, 서버 세션(Claude). 검토: Codex gpt-6-astra (R2, 핑퐁 최대 3라운드).
- **v0.4 → v0.5 변경 사유(태양 정정)**: "내 PC에서 하는 게 아니라 온라인 버전. 주소만 주면 사장님들이 자기 플레이스 주소 붙여넣고 검사." 원래 핵심 요구 = **플레이스 주소 입력 → 기존 정보·대표키워드 분석 → 개선안 + Q&A 설명 생성.** v0.4의 "사장님이 19문항에 답하는" 정적 셀프 체크는 **폴백**으로 강등하고, 자동 판독을 본선으로 올린다.
- 원칙 유지: marketing-lab과 별개 저장소, 그쪽 계약(원장·게이트·계보·티어·승인) 미적용, 가볍게. 약관·보안은 검토 범위 밖(태양 지시).

## 0. 실측 — 자동 판독이 되는가 (2026-09-14 18:50, 이 서버 IP)

| 시도 | 결과 |
|---|---|
| `m.place.naver.com/restaurant/{id}/home` 단순 fetch | **429** (이 IP는 순위추적기로 이미 요주의) |
| `pcmap.place.naver.com/restaurant/{id}/home` 단순 fetch (PC UA) | **200, 559KB**, 브라우저 없이 `window.__APOLLO_STATE__` JSON 내장 |

키세카츠 안국역점(2086785604)에서 실제로 뽑힌 값: `name, category('돈가스'), roadAddress, phone/virtualPhone(0507 스마트콜), talktalkUrl, conveniences[10](주차·예약·포장·배달·단체…), openingHours, hideBusinessHours, missingInfo, visitorReviewsTotal 1426 / avgRating 4.83, cafeBlogReviewsTotal, naverBlog, Menu 46건(name·price·description·images·recommend), FsasReview(블로그 리뷰: date·title·url), SubwayStationInfo('안국'), microReviews, paymentInfo, VisitorReviewStats(scores)`.

**미확인(구현 스파이크 1순위)**: `keywords`(대표키워드) 필드 위치, `description`(상세설명 — 이 매장은 빈 값이라 키 존재만 확인), 사진 수(`/photo` 탭 별도 요청 추정), 새소식(`/feed` 추정), 방문자 리뷰 최신 날짜·사장님 답글(`/review` 추정), 쿠폰, 예약 활성 플래그. 스파이크에서 홈 외 탭 1~3개 추가 fetch로 확보 가능한지 확인. 확보 안 되는 항목은 자동 unknown → 사장님 보충 질문으로 넘긴다(§3).

결론: **브라우저·크롤러 프레임워크 없이 HTML 1~4회 fetch + JSON 파싱으로 자동 분석 가능.** 리스크는 차단(429)이며 §5에서 다룬다.

## 1. 한 줄 정의

**사장님이 플레이스 URL을 붙여넣으면, 서버가 그 페이지의 공개 정보를 읽어 완성도 점수·대표키워드 진단과 추천·개선안·Q&A식 상세설명 초안을 한 화면에 보여주는 무료 웹 서비스.** 서버 1개(Node, 의존성 0), 로그인 없음, 원문 저장 없음(파싱된 사실만 24시간 캐시).

## 2. 흐름

```
[입력] URL 붙여넣기 (m.place / pcmap.place / map.naver.com/p/entry/place/{id} / naver.me 단축 — placeId 추출; 실패 시 "URL을 확인해 주세요")
   ↓ POST /api/check {url}
[서버] placeId → 캐시 hit(24h)면 즉시 / miss면 큐 → pcmap 홈(+필요 탭) fetch → __APOLLO_STATE__ 파싱 → facts
   ↓ facts → computeScore / analyzeKeywords / buildDraft (전부 순수 함수, v0.4 것 재사용)
[화면] ① 점수·등급·그룹 막대 ② 이번 주 할 일 3 ③ 항목 카드 ④ 대표키워드: 현재 진단 + 추천 10 ⑤ Q&A 상세설명 초안 + 복사 ⑥ 결과 텍스트 복사
   ↓ 자동으로 못 읽은 항목(unknown)만
[보충 질문] 최대 5문항 (v0.4 문항 재사용) → 재계산 (서버 왕복 없음, 브라우저 계산)
   ↓ fetch 차단·실패 시
[폴백] v0.4 19문항 셀프 체크 전체 폼 — "지금 네이버에서 정보를 못 읽어와서 직접 답해 주세요"
```

## 3. 항목표 v5 — 19문항, 자동/보충 구분

배점·전이 규칙은 v0.4 §2.0~2.1 그대로(합 100, A20/B40/C15/D25). 바뀐 건 **입력 원천** 열뿐.

| ID | 문항 | 자동 원천(facts) | 자동 판정 | 못 읽으면 |
|---|---|---|---|---|
| A1 | 전화번호 | `phone` 또는 `virtualPhone` | 있으면 pass, 둘 다 null이면 fail | — |
| A2 | 영업시간 요일별 | `openingHours` / `hideBusinessHours` | 7일 전부 → pass, 일부 → partial, 없음·hide → fail | — |
| A3 | 휴게 시간·정기휴무 | openingHours 내 breakTime/휴무 표기 | 있으면 pass, 없으면 **unknown**(우리 가게는 없음일 수 있음) | 보충 질문 |
| A4 | 찾아오는 길 | 홈 `way`/`directions` 류 필드 (스파이크 확인) | 있으면 pass / 없으면 fail | 미확인 시 보충 |
| B1 | 상세설명 글자 수 | `description` | ≥200 pass / 1~199 partial / 빈 값 fail | — |
| B2 | 대표키워드 개수 | `keywords`(스파이크) | 5 pass / 1~4 partial / 0 fail | 보충 질문 |
| B3 | 메뉴+가격 | `Menu[]` price | price 있는 메뉴 ≥1 pass / 메뉴만 partial / 0 fail | — |
| B4 | 메뉴 사진 | `Menu[].images` | 이미지 있는 메뉴 ≥1 pass / 0 fail | — |
| B5 | 사진 수 | `/photo` 탭 총수(스파이크) | ≥20 / 5~19 / 0~4 | 보충 질문 |
| B6 | 최근 소식 날짜 | `/feed`(스파이크) | ≤30일 / 31~90 / >90·없음 | 보충 질문 |
| B7 | 홈페이지·SNS | `homepages` / `naverBlog` | 있으면 pass / 없으면 fail | — |
| C1 | 네이버 예약 | conveniences '예약' 또는 예약 플래그 | 있으면 pass / 없으면 **unknown**(업종상 n/a 가능) | 보충 질문(켬/끔/안 받는 업종) |
| C2 | 톡톡·스마트콜 | `talktalkUrl` / `virtualPhone` 0507 | 하나라도 있으면 pass / 없으면 fail | — |
| C3 | 쿠폰·이벤트 | 쿠폰 필드(스파이크) | 있으면 pass / 없으면 fail | 미확인 시 보충 |
| C4 | 편의시설·주차 | `conveniences` | 1개 이상 pass / 0 fail | — |
| D1 | 최근 방문자 리뷰 날짜 | `/review` 최신 1건 날짜(스파이크) | ≤90 / 91~180 / >180·없음 | 보충 질문 |
| D2 | 최근 사장님 답글 날짜 | `/review` 답글(스파이크) | ≤30 / 31~90 / >90·없음, D1 없음이면 n/a | 보충 질문 |
| D3 | 주의 표현 | `description` + 소식 본문 | 사전 매칭: 검출 fail / 미검출 pass / 본문 없음 unknown | — |

- 자동 판정 원칙: **필드가 없다고 fail이 아니다** — 파서가 그 필드를 못 찾으면 unknown(A3·C1처럼 의미상 모호한 것 포함). fail은 필드가 있고 값이 비었을 때만.
- 보충 질문은 unknown인 것만, 최대 5개, 나머지는 unknown 유지(감점 없음, 분모 잔류).

## 4. 대표키워드·Q&A — 자동화된 부분

- **키워드 진단(§2.5 v0.4 규칙 동일)**: 현재 키워드는 `keywords` 자동. 지역 토큰 = `roadAddress`의 구·동 + `SubwayStationInfo` 역명 자동 추출. 업종 = `category`. 메뉴 = `Menu[]` 중 `recommend:true` 우선 상위 2개 이름(괄호·세트 표기 제거). → 추천 10개가 **입력 0으로** 나온다.
- **노출 셀프체크**: 유지(사장님이 지도 검색). 자동 순위 측정은 안 한다 — 검색 결과 페이지가 캡차 차단 실사례(순위추적기).
- **Q&A 초안(§2.6 v0.4 템플릿 동일)**: 업체명·역·동·업종·메뉴+가격·영업시간·주차(conveniences)·예약·포장·배달·단체 전부 facts에서 자동. 사장님 입력은 "한 줄 자랑" 1개(선택).
- GEO 효과 문구: "AI 검색이 읽기 쉬운 질문-답 구조"까지만. 네이버 AI 브리핑은 리뷰 요약이라 상세설명 인용 근거 없음 → "노출 보장" 류 표현 금지.

## 5. 서버·차단 대응 (가볍게, 그러나 이게 실패하면 제품이 없다)

- Node 단일 프로세스, 외부 패키지 0. `POST /api/check`, 정적 `index.html`.
- **큐**: 동시 fetch 1, 요청 간 1.5초 간격 → 시간당 최대 약 2,000회. 오픈채팅 게시 직후 폭주 시 대기 순번 표시.
- **캐시**: placeId별 facts JSON 24시간(파일 1개). 같은 매장 재검사는 fetch 0.
- **IP 제한**: 요청자 IP당 분당 3회.
- **차단 감지**: 429·캡차 문구·APOLLO 미검출 → 즉시 폴백 모드(§2) + 30분 쿨다운 후 재시도. 폴백에서도 점수·키워드·Q&A는 사장님 입력으로 전부 동작(v0.4).
- **UA**: PC 크롬 고정. 실측상 pcmap이 m.place보다 관대.
- **호스팅 결정 필요(E6)**: 이 데스크톱 서버(사무실 IP, 이미 429 이력)는 부적합. 클라우드 소형 VM(서울 리전)에서 **스파이크 첫 작업 = 그 IP로 pcmap 200 확인**. 데이터센터 IP 차단이면 대안: 사장님 브라우저에서 직접 읽기(CORS로 불가) → 확장 프로그램(모바일 불가) → 현실적으로 폴백(셀프 체크)만 남는다. 이 경우 태양 재결정.

## 7. 검증 절차

1. 코덱스 R2(이 문서): §3 자동 판정 규칙의 결정론·"없음≠fail" 일관성, §4 자동 추출 규칙 반례, §5 큐·캐시·폴백 상태 전이 모순, §0 미확인 필드 목록 누락.
2. 스파이크(구현 착수 전, 반나절): 클라우드 IP에서 pcmap 200 여부 + 미확인 필드 7종 위치 확정 → 결과를 이 문서 §0에 갱신.
3. 구현 → `node --test` → 코덱스 코드 리뷰 1회 → 태양 실사용(자사 4매장) → 배포.
