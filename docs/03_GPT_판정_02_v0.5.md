## 0 총평(수용/조건부/반려)

**판정: 조건부. 자동 판독 스파이크는 진행 가능하나, 채점·요청 처리 구현 전 아래 Blocker 2건을 해소해야 한다.**

Blocker 2건·Major 11건. Blocker는 같은 입력의 판정과 계산 결과가 문서만으로 하나로 정해지지 않는 경우에 한정했다. 나머지는 기존 기능의 오판·미완료 경로를 수정하는 지적이다. 약관·보안·법률·사업성 및 별개 제품의 계약은 검토하지 않았다.

핵심은 공개 페이지의 빈 값이 곧 관리 항목의 미등록을 증명하지 않는다는 점이다. §3 공통 원칙은 옳지만 개별 행과 합성 필드의 규칙이 이를 끝까지 구현하지 못한다. 또한 v0.4의 수동 입력을 자동 facts로 바꾸면서 메뉴판 사진, 네이버 예약, 진행 중 이벤트, 최신 답글의 의미가 좁아지거나 달라졌다.

### R2-1 | Blocker | §3 전 항목의 결측·빈 값 판정

**근거:** 공통 원칙은 “파서가 그 필드를 못 찾으면 unknown”, 개별 행은 A2 “없음·hide → fail”, A4·B7·C2·C3 “없으면 fail”, B3·B4·C4 “0 fail”로 적었다. A1·B1 등은 보충란도 `—`다.

**문제:** 필드 미검출을 null/빈 배열로 바꾸는 순간 unknown과 fail이 구별되지 않는다. 예를 들어 `{phone:null}`에서 `virtualPhone`은 누락됐고, `{Menu:[{name:'정식'}]}`에서 price와 images는 누락됐다. 이를 “둘 다 없음”, “가격 없는 메뉴”, “이미지 0”으로 처리하면 미관측을 감점한다. OR 조건의 한쪽만 빈 값이어도 부재가 확정되지 않는다. 같은 facts를 행 우선으로 읽는 구현과 공통 원칙 우선으로 읽는 구현의 상태가 달라진다.

**제안:** 공통 원칙 우선을 명시하고 모든 행의 `못 읽으면`을 unknown/보충 대상 가능으로 통일한다. 파서는 최소한 `미관측·유효한 값·확인된 빈 값`을 구별한다. 타입 오류·미해결 참조·일부 탭 실패도 미관측이다. OR 항목은 유효한 긍정 증거 하나면 pass, 모든 관련 원천의 부재를 확인했을 때만 fail, 나머지는 unknown이다. null이 실제 미등록을 의미하는지도 스파이크에서 확인한다. 별도 대형 체계는 필요 없고 필드별 판독 여부만 보존하면 된다.

### R2-2 | Blocker | §3 보충 재계산·v0.4 §2.2 산식

**근거:** “unknown 감점 없음, 분모 잔류”, “n/a 분모 제외”, coverage 경계는 있으나 현재 기준 문서에는 earned·score의 산식과 반올림 순서가 없다. v0.5는 v0.4 §2.0~2.1을 그대로 참조한다.

**문제:** 적용 배점 P=100, known 배점 K=70, known에서 획득한 배점 E=35라면 `100×E/K=50`과 `100×(E+unknown배점)/P=65` 모두 unknown을 직접 감점하지 않는 해석이 가능하다. 점수 등급은 각각 D와 C다. 따라서 “그대로 재사용”할 계산이 문서상 하나로 고정되지 않았다. n/a 전환 시 known까지 같이 갱신하지 않으면 coverage도 틀린다.

**제안:** 독립 제품 문서에 산식을 직접 확정한다. 가벼운 권고안은 `P=pass+partial+fail+unknown 배점`, `K=pass+partial+fail 배점`, `E=pass 배점+0.5×partial 배점`, `coverage=K/P`, `score=100×E/K`이다. unknown은 coverage의 분모에는 남고 점수 계산에서는 제외된다. K=0이면 점수·등급 없음. 등급을 원점수 기준으로 정할지 표시 반올림 뒤 정할지도 고정한다. 이는 권고 산식이며 기존 산식이 이미 이와 같다고 단정하지 않는다.

보충 때 자동 원답과 유효한 수동 보충값을 합쳐 **19항목 전체를 다시 판정·집계**한다. state 문자열만 원답 대신 넘기지 않는다(v0.4 computeScore는 rawValue를 받는다). 예를 들어 D1 unknown, D2 unknown, 나머지 82점 pass일 때 보충으로 D1=`리뷰 없음`을 받으면 D1 fail(8), D2 n/a(10), P=90, K=90, E=82, coverage=1이다. D2가 unknown으로 남으면 K=90/P=100=0.90으로 다른 결과가 된다. A3·C1 n/a도 동일하게 분모에서 제외한다.

### R2-3 | Major | §3 A2·B4·B5·C1·C3·C4와 v0.4의 의미 불일치

**근거:** v0.4는 B4 ‘메뉴판 사진 또는 메뉴 이미지’, C1 ‘네이버 예약을 켰나요’, C3 ‘진행 중인 쿠폰이나 이벤트’, C4 ‘편의시설·주차 정보를 등록했나요’다. 55-B는 메뉴판 사진과 메뉴 이미지를 별도로 열거하고, 사진에 자동 수집 사진이 함께 표시될 수 있음 및 별도 주차 정보도 기록한다.

**문제/반례:**

- A2: `월~금 09:00~18:00, 토·일 휴무`는 요일 7개 정보가 있지만 레코드는 3개일 수 있다. `매일 00:00~24:00`도 레코드 하나다. hide=true인 등록 시간은 비공개일 수 있어 ‘미등록’과 동치가 아니다.
- B4: 메뉴판 사진 1장, Menu[].images는 전부 빈 값 → v0.4 pass, v0.5 fail.
- B5: 업체 등록사진 0장, 방문자 사진 100장 → 탭 전체 수를 쓰면 등록사진 질문에 pass를 준다.
- C1: 전화 예약만 받고 conveniences에 ‘예약’이 있음 → 네이버 예약을 끈 매장도 pass 및 Q&A ‘네이버 예약’으로 오인 가능.
- C3: 만료된 쿠폰 객체가 남아 있음 → pass 오판. 쿠폰은 없지만 진행 중 이벤트 소식이 있음 → fail 오판.
- C4: `conveniences=[]`, 별도 주차 정보에 ‘주차 불가’ 명시 → 정보 등록을 묻는 v0.4에서는 pass일 수 있는데 v0.5는 fail.

**제안:** 채점 문항은 유지하고 자동 매핑을 문항 의미에 맞춘다. A2는 휴무 포함 요일별 정보 충족 여부를 계산한다. B4는 메뉴판 사진 원천도 포함한다. B5는 사진 총수의 범위를 확인한다. C1은 네이버 예약 활성 확인으로 한정한다. C3는 기준일에 유효한 쿠폰/이벤트를 확인한다. C4는 등록 여부와 제공 여부를 구별한다. 확보 불가능한 경우 unknown으로 남기면 되며 추가 수집 기능을 무조건 늘릴 필요는 없다.

### R2-4 | Major | §3 B6·D1·D2·D3의 일부 수집을 전체로 취급

**근거:** D1은 `/review 최신 1건`, D2는 `/review 답글`, D3는 `description + 소식 본문`이다. §0에서 실측된 날짜는 FsasReview(블로그 리뷰)이고 방문자 리뷰 날짜·답글은 미확인이다.

**문제:** 최신 방문자 리뷰에 답글이 없어도 오래된 리뷰에 어제 단 답글이 있을 수 있다. 첫 리뷰의 답글 부재는 ‘답글 단 적 없음’이 아니다. 소식도 고정 게시물·수정일 정렬이면 첫 항목이 최근 작성일이 아니다. 상세설명만 깨끗하고 못 읽은 소식에 사전 표현이 있으면 D3 ‘미검출 pass’는 검사 범위를 과장한다. FsasReview 날짜를 D1에 대입하면 리뷰 종류 자체가 바뀐다.

**제안:** 방문자 리뷰와 블로그 리뷰를 구별하고 날짜 필드의 의미·정렬을 확정한다. D2의 최신 답글을 현재 요청 예산에서 증명하지 못하면 unknown/날짜 보충으로 처리한다. D3는 검사할 소식 범위를 정하고 부분 수집의 미검출은 unknown, 검출은 fail로 한다. 원문이 확인된 빈 값인 것과 읽기 실패를 구별한다.

### R2-5 | Major | §2~3 최대 5개 보충 질문·폴백 입력

**근거:** unknown만 최대 5개 질문하지만 선정 순서·한도 적용 단위가 없고, 폴백은 ‘19문항 셀프 체크 전체 폼’으로 기술한다. v0.4 §2.5~2.6에는 점수 문항과 별개인 키워드·초안 입력이 있다.

**문제:** 매 재계산마다 5개를 새로 채우면 총 5개 한도를 넘는다. 처음 5개를 고정하면 D1=`리뷰 없음` 응답으로 불필요해진 D2가 자리를 낭비할 수 있다. 19문항의 B2 ‘개수 5’는 키워드 문자열을 복원하지 못하고, A1 ‘예’나 B3 ‘가격 포함’도 업체명·메뉴·가격을 복원하지 못한다. 점수는 보충되지만 키워드 진단·Q&A가 전부 동작한다는 약속은 성립하지 않는다.

**제안:** 진단 1회에서 보여줄 최대 5개 ID와 고정 우선순위를 정한다(예: 문항표 순서, D1을 D2보다 먼저 평가). 종속 변경으로 D2가 n/a가 되면 숨기되 대체 질문 여부·총한도도 명시한다. 보충 응답은 해당 세션의 answers에만 합치고 공유 facts 캐시에 쓰지 않는다. 자동 화면은 확보된 문자열만으로 진단/초안을 만들고 모르는 부분은 생략한다. 전체 폴백은 기존 v0.4의 키워드·초안 입력 탭까지 포함한다고 명시한다. 자동 단계의 5문항에 이 별도 폼을 몰래 추가하지 않는다.

| `서울특별시 중구 세종대로 10 (태평로1가, A빌딩 101동)` | ‘동’ 끝 문자열로 101동을 지역으로 선택 | 행정 주소 부분과 건물 동 구분; ‘가’ 지명 보존 |
| 역명 `안국`, `서울역`, `역삼`, `서울역(경의중앙선)` | 무조건 ‘역’ 추가 시 서울역역; ‘역’ 문자 전체 제거 시 역삼 훼손 | 말미 접미만 정규화; 원본 역명 보존 |
| 역 후보 2개 또는 역 정보 없음 | 첫 엔터티가 가까운 역인지 불명; ‘근처’ 단정 | 해당 매장에 연결된 후보·거리/순서 기준 확인; 불명 시 생략 |
| category=`돈가스`, 메뉴=`로스카츠`, 키워드=`안국역 돈카츠` | 원문 부분 문자열 검사로 ‘뭘 파는지 없어요’ 오진 가능 | 지원하는 작은 별칭표를 두거나 동의어 미확인 진단을 보류 |
| category=`미용실 > 남성전문` 같은 복합 문자열 | v0.4 select 비교에 실패해 잘못된 기본 접미 선택 | 실측 타입·값에서 지원 업종 select로 명시 매핑 |

**제안:** 원문과 템플릿용 값을 분리하고 주소·역·업종의 최소 정규화 표 및 미추출 시 생략을 정의한다. 위 입력들은 실제 응답에 이 형식이 나온다는 주장이 아니라 현 문장만으로 안전하게 처리할 수 없는 경우다.

### R2-7 | Major | §4 메뉴 정제·추천 10개·Q&A 사실 연결

**근거:** ‘recommend:true 우선 상위 2개 이름(괄호·세트 표기 제거)’, ‘추천 10개가 입력 0으로 나온다’. v0.4는 빈 변수가 들어간 템플릿을 건너뛰고 상황 태그를 수동 선택한다.

**문제:** `돈카츠(2인 세트) 28,000원`을 `돈카츠 28,000원`으로 바꾸면 가격의 대상이 달라진다. `카레(비건)`의 괄호 삭제는 메뉴 구분을 지운다. `세트 A`의 삭제 범위도 불명확하다. recommend=true 메뉴가 3개이거나 정제 후 두 메뉴가 같으면 상위 2개의 순서·중복 처리도 미정이다. 역·메뉴2·상황 태그가 없으면 v0.4 템플릿상 10개가 나오지 않는다. conveniences만으로 혼밥·데이트 상황이나 주차 ‘근처 유료’·예약 ‘전화/네이버’를 모두 복원할 수 없다. v0.4 초안의 기본 ‘직접 조리해’도 자동으로 확보한 사실이 아니다.

**제안:** 원본 메뉴명과 가격의 연결은 Q&A에서 그대로 보존한다. 키워드용 정제는 명시한 장식 표현만 제거하고 빈 결과·중복은 제외한다. 동일 우선순위는 확인된 원래 노출 순서 등으로 고정한다. 추천은 ‘최대 10개’로 정정하고 변수 부족 시 생략한다. 상황·주차 유형·예약 방법은 확인된 facts만 매핑한다. ‘직접 조리’ 등 미확인 속성을 넣는 기본 문장은 중립 문장으로 바꾼다.

### R2-8 | Major | §5 캐시·차단·쿨다운의 전이 공백

**근거:** §2는 캐시 hit 즉시, §5는 차단 시 즉시 폴백 모드 및 30분 뒤 재시도라고만 한다. 쿨다운의 적용 범위와 대기 작업 처리, 재시도 주체가 없다.

**문제:** A 매장 요청에서 429가 난 뒤 유효 캐시가 있는 B 매장이 오면 캐시를 반환할지 전체 폴백인지 불명이다. 캐시 없는 C가 쿨다운 중 오면 큐에 쌓을지 즉시 폴백인지도 없다. 이미 대기한 요청을 그대로 실행하면 쿨다운을 깨고, 멈춘 채 응답하지 않으면 30분 대기로 남는다. 만료 직후 모든 요청이 재시도 자격을 얻는 해석도 가능하다.

**제안:** 아래처럼 기존 기능의 우선순위를 한 표로 고정한다. 이는 권고안이며 새로운 외부 서비스를 요구하지 않는다.

| 조건/사건 | 응답·전이 |
|---|---|
| 유효 facts 캐시 있음 | 쿨다운 여부와 무관하게 반환(앞단 IP 제한 정책은 R2-9에서 고정) |
| 캐시 miss + 쿨다운 중 | 큐에 추가하지 않고 즉시 기존 셀프 폼 폴백 |
| 정상 + 캐시 miss | 같은 placeId 진행 작업에 합류하거나 새 작업 하나를 큐에 추가 |
| 작업 중 차단 확인 | 새 외부 요청 중지; 쿨다운 종료시각 기록; 진행·대기 요청을 부분 결과 또는 폴백으로 종료 |
| 쿨다운 만료 | 다음 miss 작업 하나만 시험 요청; 성공하면 정상, 차단이면 그 시점부터 30분 재설정 |
| 쿨다운 중 추가 사용자 요청 | 종료시각을 연장하지 않음; 트래픽 때문에 영구 쿨다운이 되지 않게 함 |

차단을 서버 전체에 적용할지 탭별로 적용할지도 확정한다. 권고는 요청 중단은 서버 공통, 이미 읽은 정상 facts는 보존이다. 홈 성공 후 추가 탭 실패는 해당 필드 unknown인 부분 결과로 종료하고, 홈 자체 판독 불가는 전체 폴백으로 한다. 실패/폴백 결과를 정상 facts처럼 24시간 캐시하지 않는다.

### R2-9 | Major | §5 동시 폭주·큐 종료·IP 제한·요청 예산

**근거:** 동시 fetch 1, 1.5초 간격, 요청자 IP당 분당 3회, 대기 순번 표시. 매장 한 건은 1~4회 fetch다.

**문제:** 동일 placeId 요청이 동시에 cache miss이면 중복 작업이 쌓일 수 있다. 큐에서 시작할 때 캐시를 재확인하지 않으면 이미 채워진 매장도 재수집한다. fetch가 끝나지 않을 때 제한시간·슬롯 해제가 없어 뒤 요청 전체가 멈출 수 있다. POST 완료 응답만으로는 대기 중 바뀌는 순번을 전달할 수 없다. 순번 조회를 재POST로 구현하면 IP 3회 제한을 스스로 소진한다.

1.5초가 fetch 시작 간 최소 간격이라면 이론상 상한은 시간당 2,400 fetch이고 4-fetch 매장은 최대 600건/시간이다. 완료 후 1.5초 대기라면 더 낮고 응답시간에 의존한다. 문서의 ‘약 2,000회’는 매장 처리량 보장이 아니다. 2,000개 서로 다른 매장이 4회씩 요청하면 최소 12,000초(약 3시간 20분)의 시작 간격 예산이 필요하다. IP 제한은 총 대기량을 제한하지 않는다.

**제안:** 같은 매장 진행 작업 합류, 실행 직전 캐시 확인, 각 fetch 시간 제한과 모든 종료 경로의 슬롯 해제, 최대 큐 크기/최대 대기시간 초과 시 폴백을 정한다. 간격은 홈·추가 탭·단축 URL 해석에 필요한 외부 요청까지 어디에 적용되는지 명시한다. 무료 도구라면 순번은 ‘접수 시 순번’으로 단순화하고 최초 응답 전달 방식만 정해도 된다. IP 한도는 요청 접수 기준인지 새 수집 작업 기준인지, 시간창 방식, 한도 초과 응답을 고정하고 대기 확인·보충 재계산이 새 진단으로 세어지지 않게 한다.

### R2-10 | Major | §2 URL → placeId·조회 경로

**근거:** 허용 URL은 호스트 나열과 `/p/entry/place/{id}` 한 패턴뿐이고, naver.me 해석 방식 및 placeId 이후 pcmap의 업종 경로 결정이 없다.

**문제/합성 테스트 후보:**

- `https://m.place.naver.com/restaurant/2086785604`와 `/home?entry=pll#...`: 탭 없는 경로, 쿼리·프래그먼트.
- `https://pcmap.place.naver.com/place/123/home`, `.../hospital/123/review`: restaurant 외 유형과 다른 탭. 유형을 버린 뒤 restaurant로만 요청하면 지원 업종과 어긋날 수 있다.
- `https://map.naver.com/p/search/안국/place/2086785604?...`: 검색 결과 안의 place 경로.
- `https://map.naver.com/v5/entry/place/2086785604`: 구형 경로 후보.
- `https://m.map.naver.com/search2/site.naver?code=2086785604` 또는 `.../siteInfo.naver?code=2086785604`: 모바일 지도 쿼리형 후보.
- `https://naver.me/AbCd1234`: 토큰 자체에서 placeId 추출 불가. 리다이렉트 해석 실패·장소 아닌 도착지는 별도 실패 경로가 필요하다.
- 공유 문장에 URL이 포함되거나 scheme이 생략된 입력: 그대로 URL 오류인지 링크 부분을 추출할지 미정.

**제안:** 모든 후보를 무조건 지원하라는 뜻은 아니다. 지원 패턴과 명시적 미지원 패턴을 구분해 URL 파서 테스트를 둔다. ID는 확정된 경로/쿼리 위치에서만 추출하고 임의 숫자 검색은 피한다. 단축 URL은 리다이렉트 해석 후 같은 추출 규칙을 적용한다. 해석할 수 없으면 직접 플레이스 URL 안내 또는 셀프 폼 진입으로 끝낸다. 선택한 placeId로 pcmap 요청을 만드는 유형 규칙도 스파이크에서 확인한다. 위 URL의 현재 작동 여부는 이번 검토에서 확인하지 않았다.

### R2-11 | Major | §0 미확인 목록과 §3·4 의존 필드의 차집합

**근거:** §0의 미확인 7종은 keywords·description·사진 수·새소식·방문자 리뷰 날짜/답글·쿠폰·예약 플래그다. §3 A4는 별도로 ‘스파이크 확인’이라고 하지만 목록에는 빠져 있다.

**문제:** 이름 수준의 실측을 하위 필드·의미까지 확인한 것으로 취급한다. 누락은 다음과 같다.

| 빠진 항목/검증 | 의존 기능 |
|---|---|
| `way`/`directions` 실제 경로·본문 | A4, Q&A 찾아오는 길 |
| `homepages` 및 SNS 링크 형태·naverBlog 부재 시 다른 링크 | B7 |
| openingHours의 요일·범위·매일·breakTime·정기휴무 하위 구조, hideBusinessHours의 의미 | A2·A3, 영업시간 초안 |
| 메뉴판 사진의 별도 원천 | B4 |
| 사진 총수의 업체 등록/방문자/자동 수집 구분 | B5; 기존 ‘사진 수’ 미확인의 세분화 |
| 소식 본문·작성일/수정일·고정 여부, 이벤트 진행 기간·상태 | B6·C3·D3; 기존 ‘새소식’만으로 부족 |
| 답글 작성일과 최신 답글을 판별할 정렬/범위 | D2; 최신 리뷰 1건 확인과 구별 |
| conveniences 값이 단순 라벨인지 활성 서비스인지, 별도 주차 등록 정보·예약 방식 | C1·C4 및 Q&A |
| 톡톡 URL·0507 번호가 활성 상태까지 뜻하는지 | C2의 ‘켰나요’ |

**제안:** 기존 미확인 목록에 위 내용을 합쳐 위치·타입·빈 값 의미·어느 질문을 판단할 수 있는지만 기록한다. §4에는 SubwayStationInfo의 해당 매장 연결·역 후보 순서, category 매핑, Menu recommend의 순서·price 형식도 추가 확인한다. 1~4회 요청 예산에서 확보하지 못한 항목은 unknown으로 고정한다. `missingInfo`의 존재만 보고 보편적인 미등록 판정으로 대체하지 않는다.

### R2-12 | Major | §2·5 캐시와 서버/브라우저 날짜 기준

**근거:** facts 24시간 캐시, 서버 최초 계산, 브라우저 보충 재계산. v0.4는 호출자가 asOf를 주입하고 로컬 자정 날짜 차를 사용한다.

**문제:** VM의 로컬 날짜와 브라우저 날짜가 다르면 같은 B6 날짜가 한쪽에서 30일 pass, 다른 쪽에서 31일 partial이 될 수 있다. 캐시에 ‘30일 전’ 같은 상대값이나 계산 state를 넣으면 다음 날에도 pass가 남는다. 보충 질문 하나만 답했는데 무관한 날짜 점수가 바뀌는 원인도 된다.

**제안:** facts에는 절대 날짜를 보존하고 수집시각과 채점 기준일을 구별한다. 첫 진단에서 정한 기준일·시간대(예: Asia/Seoul)를 서버 결과에 포함해 보충 재계산에도 그대로 주입한다. 새로운 진단에서는 유효 캐시를 쓰더라도 새 기준일로 계산한다. 상대 날짜·연도 없는 날짜·미래 날짜의 정규화 실패는 unknown이다.

### R2-13 | Major | §6 저장 HTML 1건 회귀 전략

**근거:** 유일한 실측 매장은 설명이 빈 값이고 리뷰·메뉴가 많은 음식점이다. §6은 ‘우리 매장 1건’ 파싱 회귀만 명시한다. v0.4의 순수 채점 테스트는 참고 문서에 있지만 신규 어댑터·큐·캐시를 검증하지 않는다.

**문제:** 이 픽스처의 정상 파싱만 통과해도 필드 누락→fail, 다른 매장 엔터티 선택, 부분 탭 실패, 쿠폰 만료, 최신 답글 착각, 쿨다운 교착을 모두 놓친다. __APOLLO_STATE__라는 문자열이 보이는 것과 필요한 객체가 정상 파싱되는 것도 다르다. 반대로 해당 마커가 없는 정상/삭제/형식변경 페이지를 전부 IP 차단으로 단정하면 매장 하나의 오류가 전체 30분 폴백을 유발할 수 있다.

**제안:** 기존 실제 픽스처는 유지하고 아래 합성 케이스를 추가한다. 네트워크·대형 테스트 기반 없이 HTML 문자열, fake fetch, 주입한 시계로 충분하다.

| 층 | 최소 회귀 묶음 |
|---|---|

APOLLO 미검출은 우선 판독 실패로 분류하고 해당 요청을 종료한다. 429·명시적 캡차와 동일한 서버 공통 쿨다운을 적용할지는 별도로 확정한다. 마커 하나만으로 모든 실패 원인을 같게 처리하지 않는다.

## 2 스파이크에서 확인할 것

아래는 향후 스파이크의 확인 항목이다. 이번 검토에서는 외부 요청을 수행하지 않았다.

1. §0의 기존 미확인 항목과 R2-11 차집합을 합친 목록으로 실제 경로·타입·빈 값 의미를 확인한다. 실제로 본 값과 추정은 분리해서 기록한다.
2. __APOLLO_STATE__ 안에서 요청한 placeId의 주 엔터티와 연결된 메뉴·역·리뷰를 고를 수 있는지 확인한다. 전체 객체에서 같은 타입을 무차별 수집하지 않는다.
3. A2 요일 그룹/휴무/숨김, B4 메뉴판, B5 업체 사진 범위, C1 네이버 예약 활성, C3 진행 기간, C4 별도 주차 정보가 자동 판정 가능한지 확인한다.
4. B6·D1·D2 각각의 날짜 의미와 최신성 보장 범위를 확인한다. 추가 탭 1~3개로 최신 답글을 입증하지 못하면 D2를 unknown으로 확정한다.
5. description의 비어 있지 않은 사례, 소식 본문이 있는 사례에서 길이 산정과 D3 검사 범위를 확인한다. 현재 빈 상세설명 1건은 이 검증을 대신하지 못한다.
6. 지원 URL 유형별 placeId 및 pcmap 요청 경로 결정, 단축 URL 리다이렉트가 기존 요청 예산 안에서 어떻게 처리되는지 확인한다.
7. 서버 IP의 200 여부와 홈+추가 탭에서 얻는 사실의 범위를 확인한다. 200 성공 하나로 19개 전부의 판독 가능을 결론내리지 않는다. 정상·부분 결과·전체 폴백의 구분까지 기록한다.
8. 신규 실측을 많이 늘리기보다 필요한 최소 사례와 합성 변형을 조합한다. 확인 불가능한 항목을 계속 수집하려고 범위를 넓히지 말고 unknown/기존 보충으로 종료한다.

## 3 구현 착수 전 체크리스트

- [ ] R2-1: 19행 모두 미관측·확인된 빈 값·유효 값의 판정이 하나로 정해지고, OR·부분 수집·타입 오류가 unknown으로 보존된다.
- [ ] R2-2: score·coverage·partial 계수·n/a·0 known·등급 반올림 순서를 독립 문서에 명시한다. D1=`리뷰 없음` 사례의 P=90, K=90을 재현한다.
- [ ] R2-3~4: v0.4 문항 의미를 유지하는 자동 원천만 사용한다. 확인 불가능한 부정/최신성은 unknown으로 확정한다.
- [ ] R2-5: 최대 5개의 선정·교체·총한도와 D1→D2 종속 갱신을 정한다. 전체 폴백에 기존 키워드·초안 입력을 포함한다.
- [ ] R2-6~7: 주소·역·업종·메뉴 정규화와 동률 순서를 정한다. 추천은 최대 10개, Q&A는 확보된 사실과 원래 메뉴 가격 관계만 사용한다.
- [ ] R2-8~9: 캐시·IP 제한·큐·쿨다운의 우선순위 및 모든 요청의 종료 경로를 한 가지로 정한다. timeout·대기 상한·동일 매장 합류·간격 단위를 명시한다.
- [ ] R2-10: 지원 URL 목록과 업종별 조회 경로, 단축 해석 실패 시 종료 화면을 정한다.
- [ ] R2-11~12: 실측 목록을 보완하고 필드별 판독 여부, 절대 날짜, 수집시각, 진단 기준일을 보존한다.
- [ ] R2-13: 실제 픽스처 1건 외 합성 파서·어댑터·상태 전이 회귀를 검증 절차에 포함한다. 구현 후 이를 통과시킨다.

조건 충족 여부는 위 동작 규칙과 회귀 결과로 판단한다. 과거 계약 복원이나 무료 서비스 범위 확대는 수용 조건이 아니다.
